## 1. MCP 서버 특화 설계 패턴

### 1.1 도구 세분성 (Tool Granularity)
- **너무 잘게 쪼갠 도구(Micro-tools) 지양**:
  - 나쁜 예: `open_file`, `read_line`, `close_file` 등 저수준 시스템 호출을 그대로 노출하는 경우.
  - 문제점: LLM이 3~5번의 대화 턴을 소모하며 컨텍스트를 낭비하고, 중간 단계에서 실패하거나 길을 잃을 확률이 급증한다.
- **거대한 단일 도구(Mega-tools) 지양**:
  - 나쁜 예: `manage_system(action: str, payload: dict)` 처럼 모든 처리를 하나의 도구에 욱여넣는 경우.
  - 문제점: 파라미터 스키마가 불명확해져 LLM이 환각(Hallucination)을 일으키고, 어떤 인자가 필수인지 모델이 판단하지 못한다.
- **적정 단위 (Atomic Task-oriented Tools)**:
  - 사용자나 LLM의 목표 의도에 부합하는 하나의 완성된 작업 단위로 설계한다 (예: `read_file_slice(path, start_line, end_line)`).
  - 작업 완결성: 도구 하나가 성공하면 시스템이나 비즈니스 목표가 하나의 온전한 상태에 도달해야 한다.

### 1.2 Tool Description 작성 기법 (LLM Prompt Engineering)
- **Docstring은 곧 LLM의 시스템 프롬프트다**:
  - LLM은 파이썬 함수 내부 코드를 보지 못한다. 오직 도구 이름과 Docstring(Description), 그리고 인자 스키마만 보고 도구 호출을 결정한다.
  - 따라서 함수 Docstring은 사람이 아닌 **LLM을 위한 지시문**으로 작성한다.
- **필수 4대 구성 요소**:
  1. **동작 요약**: 도구가 무엇을 하는지 한 문장으로 명확히 선언.
  2. **사용 시점 (When to use)**: 어떤 맥락이나 요구가 들어왔을 때 이 도구를 선택해야 하는지 명시.
  3. **사용 금지 / 대안 (When NOT to use)**: 헷갈리기 쉬운 다른 도구와의 경계를 긋고 대안 도구를 안내.
  4. **인자 포맷 예시**: 날짜 포맷(`YYYY-MM-DD`), 경로 규칙(상대 경로 vs 절대 경로), 단위 등을 명확히 기재.

### 1.3 FastMCP vs Low-level SDK 선택 기준
- **FastMCP 권장 대상 (대부분의 표준 MCP 서버)**:
  - 표준적인 Tools, Resources, Prompts 개발.
  - 타입 힌트와 Docstring 기반으로 자동 JSON Schema 생성이 필요한 경우.
  - 보일러플레이트 코드를 최소화하고 빠른 개발 속도가 필요한 경우.
- **Low-level SDK (`mcp.server.lowlevel.Server`) 권장 대상**:
  - 커스텀 JSON-RPC 메서드를 처리하거나 원시 프로토콜 프레임을 직접 조작해야 할 때.
  - 복잡한 다중 클라이언트 세션 격리나 세밀한 수명주기 훅(Hook)이 필요할 때.
- **계층 분리 원칙**:
  - FastMCP 데코레이터(`@mcp.tool()`)가 붙은 함수는 얇은 어댑터(Adapter) 역할만 수행하고, 실제 비즈니스 로직은 순수 파이썬 모듈(`services/` 또는 `core/`)로 분리한다. 이렇게 해야 FastMCP 의존성 없이도 단위 테스트를 쉽게 돌릴 수 있다.

### 1.4 멱등성(Idempotency) 및 부작용(Side-effect) 최소화
- **LLM의 재시도 성향 대비**:
  - 네트워크 지연이나 응답 파싱 실패 시 LLM은 동일한 도구를 동일한 인자로 다시 호출하려는 경향이 있다.
  - 상태를 변경하는 도구는 가급적 멱등(Idempotent)하게 설계한다 (예: `create_or_update`, 유니크 키 기반 중복 생성 차단).
- **파괴적 작업의 안전장치**:
  - 파일 삭제, 레코드 드롭 등 되돌리기 비싼 작업은 "드라이 런(dry_run=True)" 옵션을 제공하거나 영향 받는 항목 수를 명시적으로 반환한다.

## 2. 상태 관리 (State Management)

- **원칙: Stateless First**:
  - MCP 서버는 가능한 한 상태를 메모리에 들고 있지 않는 무상태(Stateless) 구조를 지향한다.
  - 클라이언트가 재연결되거나 프로세스가 재시작되어도 다음 요청을 독립적으로 처리할 수 있어야 한다.
- **상태 영속화 필요 시**:
  - 메모리 변수가 아닌 로컬 파일(SQLite, JSON)에 명시적으로 기록한다.
  - 작업 컨텍스트가 필요한 경우 도구 인자로 세션 ID나 토큰을 명시적으로 주고받는다.

## 3. 실패 처리 (Error Handling)

- **Silent failure 절대 금지**:
  - 예외를 조용히 `except: pass` 처리하면 LLM은 작업이 성공한 줄 알고 다음 단계로 넘어가 더 큰 오류를 초래한다.
- **자가 복구 유도 에러 메시지 (Self-correcting Error Message)**:
  - 에러 메시지는 단순 실패 통보가 아니라 LLM이 인자를 어떻게 고쳐야 할지 가이드를 주어야 한다.
  - 나쁜 예: `Error: invalid parameter`
  - 좋은 예: `Error: Directory '/data/images' not found. Available directories are: ['/data/docs', '/data/logs']`
- **스택트레이스 유출 방지**:
  - 파이썬 트레이스백 전체를 반환하면 LLM의 컨텍스트 윈도우가 오염되고 혼란을 준다. 원인은 내부 stderr 로그에 남기고, 클라이언트에는 요약된 원인과 해결책만 반환한다.

## 4. 보안 기본값 (Fail-Closed)

- **경로 이탈(Path Traversal) 원천 차단**:
  - 클라이언트가 `../../etc/passwd` 같은 악의적 상대 경로를 넘길 수 있다.
  - 모든 파일 경로는 허용된 기준 디렉토리(Base Directory)를 기준으로 `Path(path).resolve()`를 수행한 뒤, `resolved_path.is_relative_to(base_dir)` 여부를 반드시 검사한다.
- **OS 명령 실행 격리**:
  - `subprocess.run(shell=True)`나 `os.system()`은 원천 금지한다.
  - 인자 목록을 리스트로 전달하고(`shell=False`), 허용된 실행 파일 화이트리스트를 검증한다.
- **인증 정보 격리**:
  - API 토큰, DB 패스워드는 환경변수(`os.environ`)로만 주입받으며 도구 반환값이나 로그에 노출되지 않도록 마스킹한다.

## 5. 구조 및 확장성

- **테스트 가능성을 위한 최소 추상화는 YAGNI 위반이 아니다.**
  - 외부 API 클라이언트나 파일시스템 I/O는 인터페이스나 함수 단위로 분리하여 테스트 시 쉽게 mock할 수 있게 만든다.
- **전송 계층(Transport)과 도구 로직의 분리**:
  - stdio, SSE, Stream 등 전송 방식이 바뀌더라도 도구 핸들러 코드는 단 한 줄도 수정되지 않아야 한다.
- **exhaustive match / Enum 활용**:
  - 고정된 옵션을 받는 도구 인자는 문자열 대신 `Enum`이나 `Literal`을 사용하여 Pydantic 스키마 단계에서 잘못된 입력을 즉시 걸러낸다.
