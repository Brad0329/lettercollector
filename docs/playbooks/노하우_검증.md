# 노하우: 검증 (테스트가 실제로 무언가를 잡게 만드는 법)

> 출처: 프로젝트 실측(2026-08~). Python MCP Server 시스템 적용.

---

## 1. 테스트 자체를 검증하기

- **새 대조 테스트는 일부러 틀리게 해서 실패를 한 번 본다.** 통과만 보면 아무것도 검증하지 않는 테스트를 통과로 착각한다.
- **변이(mutation) 확인은 두 단계 다 본다**:
  ① 변이가 실제로 적용됐는지
  ② 테스트가 실패하는지.
  버그를 고쳤으면 회귀 테스트를 넣고, 고침을 되돌려 **그 테스트가** 실패하는 것을 한 번 본다 (`AGENTS.md` '검증 강도' 사다리).
- **변이는 한 번에 하나씩.**
- **"안 깨진다"류 테스트는 무엇으로 깨짐을 감지하는지부터 검증한다.**
- **픽스처가 없어서 통과하는 테스트는 아무것도 검증하지 않는다.**
- **회귀 테스트의 입력 데이터는 충돌·경계가 실제로 발생하는 값으로 고른다.**

## 2. MCP 서버 특화 검증 4단계 (Verification Ladder)

MCP 서버는 일반 웹 API와 달리 **JSON-RPC 2.0 프로토콜, stdio 전송, LLM의 추론**이라는 세 가지 특수 계층이 얽혀 있다. 아래 4단계는 서로 대체될 수 없으며 순서대로 검증해야 한다.

```
[1단계: Pytest 유닛 테스트] ──> [2단계: 스키마 검증] ──> [3단계: MCP Inspector] ──> [4단계: 실 클라이언트 연동]
```

### 1단계: 유닛 테스트 (pytest + In-memory Client)
- **도구 로직 격리 검증**: 외부 프로세스나 실제 LLM 없이 파이썬 레벨에서 도구 함수를 직접 호출하여 비즈니스 로직, 경계값, 예외 처리를 검증한다.
- **In-memory Mocking**: 파일시스템, 외부 HTTP 호출, DB 접근 등은 mock/fixture(`pytest-mock`, `respx` 등)를 사용하여 결정론적(deterministic)으로 테스트한다.
- **에러 응답 규약 검증**: 유효하지 않은 인자 전달 시 프로세스가 크래시되지 않고, 적절한 에러 메시지나 `isError=True`를 반환하는지 확인한다.

### 2단계: 스키마 검증 (Schema & Pydantic Validation)
- **Pydantic 스키마 일치**: 도구의 타입 힌트와 `Field(...)` 제약 조건이 의도한 JSON Schema로 컴파일되는지 확인한다.
- **스펙 문서(`docs/TOOLS.md`) 대조**: 코드 상의 함수 시그니처(인자명, 필수 여부, 기본값, docstring)가 `docs/TOOLS.md`의 정의와 정확히 일치하는지 `spec-checker`로 검증한다.
- **Docstring 누락 방지**: 모든 도구 함수가 LLM이 이해할 수 있는 명확한 docstring(설명, 사용 시점, 인자 설명)을 갖추었는지 확인한다.

### 3단계: 프로토콜 검증 (MCP Inspector)
- **실제 stdio 통신 테스트**: `npx @modelcontextprotocol/inspector python src/server.py` 명령으로 공식 MCP Inspector를 띄운다.
- **도구 목록 조회 (`tools/list`)**: 브라우저 UI에서 서버가 제공하는 모든 Tools, Resources, Prompts 목록이 정상 렌더링되는지 확인한다.
- **도구 수동 호출 (`tools/call`)**: UI에서 파라미터를 입력하고 실제 호출하여 JSON-RPC 요청/응답 왕복(Round-trip)이 에러 없이 완결되는지 확인한다.
- **로그 및 스트림 확인**: 서버 로그가 stdio 프레임을 오염시키지 않고 inspector의 로그 뷰어에 올바르게 들어오는지 검증한다.

### 4단계: 실 클라이언트(Claude Desktop / Antigravity) 연동 검증
- **호스트 등록**: `claude_desktop_config.json` 또는 Antigravity MCP 설정에 등록 후 클라이언트를 재시작한다.
- **프롬프트 유도 실측**: "OO 파일을 검색해줘", "XX 데이터를 분석해줘" 같은 자연어 지시를 LLM에 입력하여 LLM이 올바른 도구를 의도대로 선택하고 실행하는지 확인한다.
- **컨텍스트 크기 점검**: 도구가 반환하는 데이터가 지나치게 방대하여 LLM의 컨텍스트 윈도우를 초과하거나 비용을 낭비하지 않는지 실측한다.

## 3. stdout 오염 검증 (Zero-stdout Check)

- **`capsys`를 활용한 회귀 테스트**:
  stdio 전송 모드에서 `stdout`에 한 줄이라도 쓰레기 데이터가 출력되면 JSON-RPC 파서가 즉시 폭파된다. 모든 테스트 파일 또는 공통 픽스처에 stdout 출력 검증을 포함한다.
  ```python
  def test_tool_does_not_pollute_stdout(capsys):
      result = my_tool(param="test")
      captured = capsys.readouterr()
      assert captured.out == "", f"stdout must be empty, but got: {captured.out}"
  ```
- **의존 라이브러리의 배너 출력 차단**: 라이브러리 임포트 시 라이선스나 환영 문구를 stdout으로 출력하는 패키지가 있는지 반드시 사전 점검한다.

## 4. 검증의 층 — 서로 대체가 안 된다

- **자동 테스트 / MCP Inspector / LLM 실대화는 잡는 결함의 층이 다르다.**
  - Pytest: 로직의 정확성, 분기 커버리지.
  - Inspector: JSON-RPC 프로토콜 적합성, JSON 스키마 직렬화.
  - LLM 실대화: 도구 설명(docstring)의 유도력, 자연어 인자 추출 정확도.
- **악의적 입력 관점 점검은 정상 경로 테스트와 별개로 필요하다.**
  - SQL 인젝션, Path Traversal(`../../etc/passwd`), 버퍼 초과 길이 입력 등.
- **눈으로 확인한 것과 테스트가 지키는 것을 구분해 기록한다.**

## 5. 실제에 가깝게 검증하기

- **가짜(fake) 목업은 실제 라이브러리의 프로토콜 파괴를 잡지 못한다.**
  - 예: mock 환경에서는 통과했으나 실제 환경에서 Windows CP949 인코딩으로 깨지는 경우.
  - 따라서 최소 1회는 실제 Python 인터프리터 프로세스를 stdio 파이프로 실행하여 왕복 테스트를 거친다.

## 6. 디버깅 원칙

- **가설을 세웠으면 수정을 되돌려서 확인한 뒤 다음으로 간다.**
- **원인 불명의 연결 끊김 (Connection Closed / Parse Error)**:
  - 십중팔구 어딘가에서 `print()`가 호출되었거나, 서드파티 라이브러리가 stdout에 로그를 뱉은 것이다.
  - stderr 스트림 로그를 확인하거나 `sys.stdout`을 가로채는 래퍼를 씌워 출력 발생지를 역추적한다.
