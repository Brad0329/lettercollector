# 노하우: 작업 트랙 — 저위험 vs 일반, 그리고 왜 이렇게 정했나

> 본문(AGENTS.md '검증 강도')에는 규칙만 있고, 여기에는 그 규칙이 왜 그 모양인지가 있다.
> 트랙 기준을 바꾸려 하거나 왜 조심하는지 궁금할 때 연다.

---

## 1. 왜 트랙이 필요한가

병목은 코딩·테스트가 아니라 **왕복 횟수**(확인 요청·대화 턴·수동 승인)라는 실측에서 출발했다.
모든 작업을 같은 무게로 다루면 한 줄짜리 로직 수정에 과도한 검증 비용(전체 프로토콜 테스트, Inspector 재기동)을 쓰게 되고, 반대로 전부 가볍게 다루면 되돌릴 수 없는 것(도구 시그니처 변경으로 인한 클라이언트 프롬프트 파괴)을 가볍게 만진다. 그래서 **"얼마나 조심할까"를 재는 자**를 하나 두고, 그 자로 갈라진 두 트랙을 둔다.

- **일반 트랙 (고위험 / 계약 변경)**:
  - 도구 시그니처 변경(인자 추가/제거/타입 변경), 신규 도구 추가, 전송 계층(stdio/SSE) 변경.
  - 검증: `docs/TOOLS.md` 승인 갱신 + pytest 전체 통과 + MCP Inspector 수동 검증 + 클라이언트 연동 대조.
- **저위험 트랙 (구현 세부사항)**:
  - 도구 내부 버그 수정, 성능 최적화, 로깅 보강, 단순 문서 수정.
  - 검증: 관련 단위 테스트(pytest) 통과 확인.

트랙의 기준은 변경의 '규모'가 아니라 **'되돌리기 비용'**이다.

---

## 2. 자를 잘못 고르면 트랙 자체가 비용이 된다

크기와 위험은 상관이 없다. 내부 헬퍼 함수의 500줄짜리 알고리즘 개선은 git으로 되돌리면 그만이지만, 도구 시그니처 한 줄의 변경은 클라이언트 LLM의 프롬프트 호출 전반을 깨뜨린다. 크기로 재면 큰 저위험 작업을 일반 트랙으로 돌려 느려지고, 작은 고위험 변경(도구 파라미터명 오타 수정 등)을 저위험으로 흘려보내 클라이언트를 고장 낸다. 따라서 기준은 항상 **"되돌리기가 비싼가(계약 위반인가)"**이다.

---

## 3. 헷갈리기 쉬운 경계 (MCP 관점)

- **Docstring 문구 개선은 저위험인가 일반인가?**
  - 단순 오타 교정은 저위험이다.
  - 그러나 LLM의 도구 선택 기준(When to use)을 바꾸는 문구 수정은 일반 트랙에 준하여 Inspector에서 스키마 반영을 확인해야 한다.
- **내부 헬퍼 함수 추가는 스펙 변경이 아니다.**
  - `src/tools/` 내부의 비공개 함수를 리팩토링하는 것은 외부에 노출되는 MCP 도구 계약에 영향을 주지 않으므로 저위험 트랙이다.

---

## 4. 테스트 변이 확인

빈 테스트(아무것도 검증하지 않으면서 초록불인 테스트)를 잡아낸 유일한 방법이 변이 확인이다.
테스트를 넣거나 고쳤을 때는 변이 확인(일부러 틀려보기)을 저위험 트랙에서도 생략하지 않는다.

---

## 5. 전제

- 일반 트랙이 필요해 보이면 에이전트는 혼자 정하지 말고 사용자에게 승인을 구한다 (`docs/TOOLS.md` 게이트).
- 반대로 명확한 저위험 변경을 일반 트랙으로 올려 시간을 낭비하지 않는다.
